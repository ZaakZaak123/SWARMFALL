# 01 — PRODUCT GDD

## 1. Elevator pitch

**SWARMFALL** — стилизованный Roblox PvE horde-shooter (одиночная игра сначала, затем кооператив), где игрок выживает под давлением инопланетного роя, поглощает свойства элитных существ и прямо за один забег превращает базовую пушку в зрелищную боевую конструкцию. Удовольствие — от **ручной стрельбы и физически понятных последствий попаданий**, а не автоматического фарма.

**Фантазия:** «Минуту назад у меня был автомат; теперь мои выстрелы запускают лавину молний, а в орде образуется коридор». Рабочий слоган: «Стань оружием против роя».

**ЦА/платформы:** Roblox, в первую очередь телефон (альбомная ориентация), затем ПК; консоль и другие типы управления — последующие задачи после проверки. Игра доступна без боевых покупок. Возрастные настройки и контент-декларации устанавливаются по фактически реализованному содержимому в Creator Dashboard — не предполагать рейтинг заранее.

## 2. Пять опор качества (по приоритету)

1. **FEEL:** даже стартовая стрельба — ударная, быстрая и читаемая; урон, импульс и смерть врага ощущаются.
2. **POWER:** явная разница между началом и концом забега (по форме оружия, плотности эффектов и тактике).
3. **CHOICE:** игрок принимает решения о сборке, которые меняют поведение оружия, а не только числа.
4. **PRESSURE:** угрозы заставляют двигаться, но игра дает «время быть невероятно сильным».
5. **REPLAY:** новые комбинации, цели мастерства и сложности важнее длинного гринда.

Антицели: пустой открытый мир, автокликер, pay-to-win, сотни перекрашенных пушек, скучная первая минута, навязчивые окна магазина, «физическая симуляция 500 Humanoid» как самоцель.

## 3. Основной цикл

**Между забегами:** выбрать одну базовую пушку + косметику/позднее класс → войти в забег → уничтожать врагов ручным прицеливанием → собирать авто-подбираемый опыт → каждые ~40–60 секунд (до 6 модификаций) выбирать 1 из 3 улучшений → убить элиту и получить гарантированный целевой компонент → эволюционировать оружие → выжить во время события → победить босса → экран результатов → расходовать металлолом/повышать мастерство → повтор.

**В начале игрок уязвим → к середине очень силён → конец проверяет собранный билд.** Не допускать постоянного отставания от повышающихся HP врагов.

## 4. Scope и временные горизонты

| Система | P1: playable slice | Release target (не сейчас) |
|---|---|---|
| Уровень | Reactor Yard, одна компактная арена | 2–3 биома + вариации |
| Забег | 8 минут ±1 | ~12 минут, другие режимы |
| Игроки | 1 | 1–4, кооперативные синергии |
| Оружие | 3 базы, из них 1 полная визуальная эволюция | 6–9 баз, несколько ветвей |
| Upgrade pool | 12 строго определённых | Расширяемый пул, анти-дубликаты |
| Враги | 4 архетипа, 1 элита-вариант, 1 босс | Новые роли и боссы |
| События | 1 скриптовое «Прорыв улья» | Пул из 5+ событий |
| Экономика | Локальный расчёт результатов, без обязательных постоянных валют | Сохраняемый профиль и метапрогрессия |
| Монетизация | Нет | Косметика после проверки удержания |

## 5. Системный порядок приоритета

**Сначала** движения/камера/стрельба/попадание/враги → затем upgrade/build variation → затем режиссёр волн и босс → затем UX → оптимизация → проверка на внешних игроках → лишь затем экономика/монетизация. Если нет желания повторного забега, приостановить расширение контента.

## 6. Пользовательские истории

- Первый пользователь за **15 секунд** двигается и стреляет без текстового обучения; за **45 секунд** видит массовую гибель существ; до **60 секунд** понимает первую модификацию.
- На **4-й минуте** видит минимум одно зрелищное изменение оружия, связанное с выбором.
- На **5–6-й минуте** встречает событие, где есть безопасное и рискованное решение.
- К **финалу** понимает причину победы/поражения и хочет попробовать альтернативную сборку.
- На слабом телефоне может понизить качество VFX, не теряя читаемость опасных атак.

## 7. Пять продуктовых принципов

- **Readable chaos:** арена яркая, но угрозы и зона попаданий различимы.
- **Meaningful randomness:** выбор случайных предложений, но получение эволюции контролируемое при собранных требованиях.
- **No dead runs:** если идеальная комбинация не пришла, существует запасной универсальный билд.
- **Fun before grind:** постоянная сила ограничена, варианты сборок открываются горизонтально.
- **Deterministic enough:** для QA директор и апгрейды поддерживают `debugSeed` в дев-среде.

## 8. Вопросы, которые НЕ считаются решёнными

Бренд/название, юридическая проверка; окончательная камера после playtest; конкретные цены косметики; финальная емкость NPC по профилю устройства; удержание и конверсия до полевых измерений. Список решений — документ 14.

# 02 — LEVEL 01 / REACTOR YARD

## 0. Задача уровня

Показать напряжённое и при этом читаемое истребление роя **в пределах одной арены**. Пространство должно постоянно раскрывать новые угрозы и интерактивные действия, но не требовать дорогого открытого мира или сложной разрушаемости. В P1 один уровень, одиночное прохождение.

**Размеры, ориентиры (design targets):** огороженная боевая площадка **360 × 320 studs**, ось X восток-плюс, Z север-плюс, центр `(0,0,0)`, игровая плоскость XZ, высота ~0; запад `x=-180`, восток `x=180`, юг `z=-160`, север `z=160`. Низкие препятствия высотой 4–10 studs, крупные декорации не перекрывают камеру. Не создавать непроходимые карманы.

Приложение `assets/LEVEL01_TOPDOWN.svg` — схематичная карта, **не точная инженерная геометрия**.

Между секторами должно быть **минимум два независимых пути**; основной проход не уже 20 studs, обход не уже 14 studs. Никаких прыжковых головоломок. Игрок не должен оказаться в тупике без рывка. Чёткие силуеты основных препятствий: контейнеры 8×18, колонны диаметром 7, защитные блоки 8×8.

## 2. Контроль пространства и дистанций

- В каждом секторе минимум 2 маршрута отхода, проверяемых без способности `Dash`.
- Цель: видимая дистанция боя 30–90 studs; просторные прямые участки до 120, без постоянного выстреливания вне экрана.
- Игровые границы — инженерный забор + непроходимый периметр, без невидимых односторонних стен. Простой обход периметра.
- Стартовая точка безопасна первые ~8 секунд, но не является постоянной неуязвимой зоной.
- Объекты у края арены не должны позволять с помощью коллизий выбраться наружу.

## 3. Интерактивные объекты: ровно 3 типа

| ID | Механика | Тайминг | Counterplay | Ограничение |
|---|---|---|---|---|
| `OBJECT_COIL` | Разрядная катушка: после активации поражает ближайших врагов в радиусе 26, визуально создаёт цепную дугу | cooldown 50с; действие 0.6с | Подойти; не стоять в точке угрозы | Сервер подтверждает диапазон, cooldown и состояние |
| `OBJECT_GATE` | 2 разрушенные створки открывают дополнительные проходы во время событий | ~2:30, ~5:30 | Телеграф на карте; всегда есть старый обход | Скриптовое переключение коллизий, **не** дорогая деструкция физикой |
| `OBJECT_HIVE` | 3 гнезда в событии: уничтожить ради прогресса или пережить таймер | ~5:30–6:20 | Взорвать три или отойти | Каждый объект HP 350; reward ограничен одним на событие |

В P1 НЕ делать крафт-станки, магазин внутри карты, автотурели, платформинг, процедурную перестройку геометрии.

## 4. Спавн и читаемость

**Потенциальные точки:** N `(0,145)`, NE `(125,130)`, E `(165,0)`, SE `(125,-130)`, S `(0,-145)`, SW `(-125,-130)`, W `(-165,0)`, NW `(-125,130)`. Это проектные центры кластеров, при размещении не выдавать монстров за периметр.

**Обязательные условия спавна:** валидная поверхность/зона прохода, не ближе **55 studs** к игроку (первичная оценка), не в прямой видимости перед носом игрока там, где это визуально нелогично; при событии допустим явно предупреждённый «прорыв» из ворот. Спавн по бюджету (не постоянный полный круг 360°), с намеренными коридорами безопасности. Перед массовым прорывом 2–3 секунды: красные сигналы и звук; камера и UI отмечают опасную сторону. В кооперативе правила вычисляются по группе/ближайшему игроку, но это после P1.

## 5. Путешествие арены за 8 минут

| Время | Состояние пространства | Принудительная задача |
|---|---|---|
| 0:00–1:00 | Зона Z0 + соседние проходы, враги с N и E | освоить движение/стрельбу |
| 1:00–2:30 | Включаются W/S точки; катушка доступна | освоить уклонение, первый выбор |
| 2:30–4:00 | Открывается 1 из 2 секционных заслонок; элита | сменить маршрут, забрать ядро |
| 4:00–5:30 | Плотные группы; доступна эволюция | проявить мощь билда |
| 5:30–6:20 | `EVENT_HIVE_BREACH`, 3 гнезда | уничтожить или пережить |
| 6:20–7:00 | короткая передышка, точечные усиленные враги | подготовка к боссу |
| 7:00–8:00 | босс с N, боковые волны ограничены | финальная кульминация |
| >8:00 | эскалация до 9:00 при живом боссе; по 9:00 поражение | не допустить бесконечного боя |

**Победа:** босс побеждён; время целевого победного прохождения 7:30–8:30. **Поражение:** HP игрока=0, или 9:00 и босс жив. Выход из сессии — без победной награды; начисление частичного прогресса в будущей мета-системе только после сохранения/правил в док.07.

## 6. Камера и препятствия

Третье лицо, фиксированное боевое возвышение: первоначально pitch **50° вниз от горизонта**, дистанция камеры ~**55 studs**, адаптивная регулировка **35–65** в зависимости от экрана/реального теста. Игрок размещён чуть ниже центра экрана, передний сектор обзора расширен. Поворот камеры/наведение — проверяемая гипотеза: свободный курсор на ПК, правый стик на mobile; камера следует за игроком плавно без заметной задержки ввода. Камеру не ставить под потолок; стены/крыши перед ней прозрачеют локально. Объекты, перекрывающие персонажа, получают локальный `fade`, не отключая серверную коллизию.

Не использовать камеру за плечом на высоте персонажа в P1: это существенно снижает контроль орды. Камера должна быть настраиваемой, но не менять collision/aim-параметры оружия.

## 7. Level art, свет, звук

День/псевдо-сумерки, контрастная среда без абсолютной темноты. Палитра: холодный бетон + бирюзовая инженерия; опасности — оранжево-красные. Враги визуально сильнее фона. На дальнем плане проблески разломов и разрушения (клиентские, не физически симулируемые). Звук каждой стороны спавна позиционируется.

## 8. Приёмка уровня

- 10 последовательных забегов: ни одного застревания у препятствий, NPC проходят все пути, 0 спавнов внутри стен/игрока.
- Игрок может пересечь каждый сектор без рывка и в любом направлении вернуться в LOOP.
- До первого выбора оружия ≤60с; элита/эволюция/событие/босс происходят в заявленных фазах.
- Взглянув на экран, тестировщик определяет угрозу кислотной атаки и направление прорыва до получения урона.
- Смены геометрии не вызывают обрыва навигации или падения с арены.

# 03 — RUN STATE / PACING / DIRECTOR

## 1. Конечный автомат

`LOBBY → PREPARE → COUNTDOWN(3s) → ACTIVE → {UPGRADE_MODAL|EVENT_ACTIVE|BOSS_ACTIVE} → {VICTORY|DEFEAT|ABORT} → RESULTS → LOBBY`

При смерти отменить активные вражеские атаки, заморозить результат забега, один раз вычислить награды; UI получает `runId` и итог. Двойная выдача награды по повторному RemoteEvent запрещена. При дисконнекте забег завершается без победных наград; судьба частичной добычи — отдельно определена в doc.07.

## 2. Временная шкала P1

| Фаза | t | Новое событие | Проверка ощущения |
|---|---|---|---|
| Entry | 0–30s | первые 8–12 слабых существ, никаких сложных угроз | «стрелять приятно» |
| Growth A | 30–90s | опыт и 1–2 выбора upgrade | «владею ситуацией» |
| Growth B | 90–150s | плевуны/ускорение; катушка | «начинаю думать» |
| Elite | 150–210s | 1 бронированная элита, выпадение ядра гарантировано | «получил редкую находку» |
| Evolution | 210–300s | гарантировать доступ к первой эволюции при минимальных действиях | «оружие реально изменилось» |
| Swarm | 300–330s | высокая плотность мелких существ | «я машина уничтожения» |
| Hive | 330–380s | три гнезда, бонус за их убийство | «короткая цель внутри хаоса» |
| Breather | 380–420s | снизить давление, дать pickup/upgrade | «передышка» |
| Boss | 420–540s | босс, победа или hard-limit в 9 минут | «финал и результат» |

Не блокировать `UPGRADE_MODAL` в соло: симуляцию ставить на паузу. В будущем коопе — upgrade выбирается из заранее подготовленного списка между фазами, и игра не встаёт на паузу для всей группы без отдельного решения.

## 3. Spawn Director: управляемое давление

Счётчик давления `pressure` 0..1 — функцию фаз и активности игрока. Каждые **0.5с** (design target) система вычисляет оставшийся бюджет активных врагов и допустимые типы. Никакой постоянной масштабируемой физики для всех юнитов.

- `baselineActiveCap = 70` обычных/элитных противников в одиночном P1 на среднем целевом телефоне — **гипотеза, корректируется профилем**, а не обещание.
- `spawnPerSecond`: начало 2–3, середина 4–6, пик 7–10, ограничено доступными слотами; число **посещений** уровня может превышать лимит одновременного количества.
- Визуальная «огромная толпа» достигается прежде всего массовой композиционной группировкой, недорогими смерть-эффектами, музыкальным подъёмом. Не создавать 500 дорогих NPC одновременно.
- `pressure` влияет на долю быстрых/дальних врагов; не подстраивать пул полностью против текущего билда.
- За одну фазу сложных приоритетных врагов не более 20% популяции; иначе орда перестаёт быть ордой.
- Интервал подсчёта урона/FX для цепей ограничен; док.04 и 09.

Постановка: два главных направления на старте → 2–3 направления в середине → короткие предсказуемые пики; на боссе мелкие враги ограничены. Система избегает «мгновенных наказаний»: никаких врагов в упор без предупреждения.

## 4. Выбор улучшений

Ориентир: 1 предложение из 3 каждые 40–60 секунд до заполнения **6 слотов модификаций** (примерно к 5:00–5:30), но не строго по таймеру — опыт от убийств. После 6-го выбора полоса опыта помечается «MAX», новых предложений больше нет; не имитировать бесконечную прокачку. **Страховка RNG:** гарантированное предложение первого модификатора до 60с; 1 шанс получить связанный ключ к эволюции к 180с; при отсутствии ключа к 210с элитная награда позволяет выбрать недостающий; к ~240с открыта гарантированная первая эволюция для игрока, который активно сражался.

В прототипе можно сначала сделать deterministic picks по одной эталонной ветви и вторую доступную ветвь, затем подключить честный weighted pool. Никогда не выдавать три бесполезных/несовместимых предложения.

## 5. Боссы и скрипты

Босс в 7:00. При живом боссе к 8:00 — режим ярости с видимым предупреждением, к 9:00 дефит (не бесконечный баланс-лок). В P1 успешное убийство всегда приводит к экрану результата, не к открытой бесконечной игре.

## 6. Random seed и тестируемость

`runSeed`, `phase`, `eventId`, `selectedUpgrades`, `evolutionId`, `bossResult` логируются в dev. Команды доступные только в Studio: задать seed, ускорить фазу, заспавнить элиту, выдать upgrade, переключить качество VFX, показать spawn debug. В опубликованной сборке dev команды недоступны обычным игрокам.

# 04 — WEAPONS / UPGRADES / EVOLUTIONS

## 1. Ключевое правило

Оружие меняет **поведение, силуэт, звук и частоту событий на экране**, а не только DPS. Выбор игрока контролируем: случайность определяет доступные предложения, но выполненная рецептура эволюции даёт конкретный результат.

## 2. Начальные оружия P1 (числа — для первого баланса)

| ID | Оружие | Стрельба | Базовая оценка | Роль |
|---|---|---|---|---|
| `W_ARC_RIFLE` | Искра (выдаётся с начала) | 6 выстрелов/с × 12 dmg, дальность 85 studs, обойма 36, reload 1.5с | ~72 DPS без перезарядки | Универсальный |
| `W_SCATTERGUN` | Вулкан | 1.2 выстрела/с × 7 дробин × 10 dmg, дальность 42, обойма 6, reload 1.8с | до ~84 DPS вблизи | Контроль толпы |
| `W_PLASMA_BEAM` | Разлом | 10 dmg за 0.1с на первой цели, дальность 70, ресурс нагрева 100, 4с до перегрева | до ~100 DPS первичной цели | Пробивание/линии |

Цифры не финальные: реальный DPS зависит от перезарядки, дальности, брони и попаданий. В P1 все три можно выдать через debug/select, но **полностью контентно и визуально** довести одну ветвь `W_ARC_RIFLE → EV_THUNDERLORD`. Остальные оружия должны быть играбельны, не обязательно иметь уникальные финальные модели.

## 3. Модификаторы P1 — ровно 12

| ID | Имя | Эффект первого уровня | Ограничение |
|---|---|---|---|
| `UPG_CHAIN` | Цепь | Каждый 6-й валидный hit переносит 40% dmg на до 2 соседних врагов в радиусе 18 | Дуги не создают новые дуги |
| `UPG_RICOCHET` | Рикошет | 1 вторичная цель на выстрел, 45% базового dmg | Рикошет не рикошетит повторно |
| `UPG_PIERCE` | Пробивание | Снаряд проходит ещё 1 противника, второму 65% dmg | cap 3 цели |
| `UPG_IGNITE` | Поджог | 4 dmg/сек 3 сек, refresh | DOT не критует |
| `UPG_DETONATE` | Детонация | Каждое 8-е убийство порождает 35 dmg в радиусе 14 | максимум 1 поколение |
| `UPG_CORRODE` | Коррозия | Hit снижает броню цели на 10% на 4с | cap 25% |
| `UPG_FREEZE` | Замедление | Снижение скорости врага на 20% на 2с | босс cap 8% |
| `UPG_MULTISHOT` | Дублирующий импульс | раз в 3с дополнительный слабый снаряд (40% dmg) | без самоповтора |
| `UPG_FIRERATE` | Стабилизатор | +12% темп стрельбы | до +36% суммарно |
| `UPG_CRIT` | Прицельный удар | +8% шанс ×1.5 dmg | max crit chance 24% |
| `UPG_DASH_SHOCK` | Импульсный рывок | Рывок наносит 20 dmg при близком касании | max 3 цели за рывок |
| `UPG_SHIELD` | Барьер | После 20 убийств щит на 20 HP на 8с | не чаще 1 раза за 20с |

Прокачка уровня отдельного upgrade в P1 — 1 уровень (не пять стаков). Для поздних релизов можно добавить ступени только после отдельного баланс-теста.

## 4. Полные эволюции — один реализационный эталон и два следующих концепта

**P1 полностью:** `EV_THUNDERLORD` («Громовержец»), базис `W_ARC_RIFLE`, ключи `UPG_CHAIN` + `UPG_RICOCHET` + гарантированный `CORE_STORM` от элиты. На 4-й минуте слот эволюции показывает явную кнопку **«Эволюционировать»**; не превращать оружие автоматически без подтверждения. Итог: цепная молния по 4 ближайшим целям, множитель вторичного урона 45%/30%/20%, max 4 события цепи в секунду на игрока, дуги **не** вызывают вторичные навыки повторно. Модель получает две видимые катушки, голубые дуги, новый звуковой слой и прицел.

**Позже:** `EV_INFERNO_GRINDER` = `W_SCATTERGUN` + `UPG_IGNITE` + `UPG_DETONATE` + `CORE_EMBER`: сплошные огненные конусы с ограниченным blast radius. **Позже:** `EV_VOID_LANCE` = `W_PLASMA_BEAM` + `UPG_PIERCE` + `UPG_CORRODE` + `CORE_VOID`: узкий дальний энергетический прокол. P1 может иметь только заглушенные описание/иконки этих форм; не объявлять их реализованными.

## 5. Реальные синергии P1 — 2

1. `SYN_CHAIN_RICOCHET`: валидный базовый рикошет попадает в ранее не поражённую цель и добавляет charge для цепи; один выстрел не более 1 дополнительного trigger charge. Визуально вспышка «DOUBLE ARC».
2. `SYN_IGNITE_DETONATE`: враг с ignite, убитый основной атакой, детонирует с +25% радиусом, но остаётся **одним** поколением, не раскручивает каскад в бесконечность.

Остальные взаимодействия — кандидатные спецификации для следующих релизов; нельзя случайно получать непроверенные эффекты при добавлении модификаторов.

## 6. Нормы баланса

- `DamageBudget`: первичный выстрел / вторичные поражения / ауры разделены по `procType`. Вторичный урон не запускает другие вторичные навыки, кроме отдельных разрешённых interaction IDs.
- На одного игрока: до **8 вторичных damage events/0.1с** и до **4 chain-visual events/сек** — начальные cap, под профилирование.
- Crit / status / splash подчиняются общему event budget.
- Игроку доступно не более 6 активных модификаторов на забег в P1 (могут предлагаться замены, но это после baseline). Нельзя собрать одновременно все 12.
- При накоплении взрывов объединять малые события в агрегированный VFX/урон с сохранением честной суммарной величины по целям.

## 7. Feel и обязательная визуальная коммуникация

Каждый выстрел: мгновенный muzzle flash, короткий звуковой удар, видимый hit marker только при подтверждённом попадании (локальное предсказание допустимо с корректировкой), разные анимации смерти по размеру врага. Upgrade выбор = читаемое «до/после» в тексте (например «1 → 2 цели»). Эволюция = 1.5–2.0с анимации с безопасной паузой в соло, затем немедленный бой.

## 8. QA-кейсы

- Две одинаковые цели и стенка: рикошет не проходит через геометрию без явного разрешения.
- Нет бесконечного `UPG_CHAIN` при массовом взрыве; limits соблюдены.
- Смена оружия не оставляет DOT, принадлежащий несуществующей сущности.
- Эволюция всегда собрана при гарантированной последовательности, ветка тестируется с детерминированным seed.
- Отключение VFX не меняет серверный damage output.

# 05 — ENEMIES, BOSS AND SPAWN BEHAVIOR

## 1. Роли противников (первичный баланс, не тестовые факты)

| ID | Роль | HP | Скорость | Урон | Особенность |
|---|---|---:|---:|---:|---|
| `EN_RUNNER` | Бегун | 24 | 14 studs/s | 7/контакт, CD 1.2с | Стаи, низкая цена спавна, быстрые смерти |
| `EN_STALKER` | Прыгун | 38 | 19 | 9/выпад, CD 3с | Заряжает прыжок 0.65с, красный телеграф |
| `EN_SPITTER` | Плевун | 62 | 8 | 6/тик в кислотном круге, max 3 тика | Дистанция 45–70, видимый круг радиусом 10 перед плевком |
| `EN_BULWARK` | Броненосец | 190 | 7 | 14/удар, CD 2с | Медленный фронтовой блокатор с уязвимым боком |
| `ELITE_BULWARK` | Элитный броненосец | 650 | 8 | 18/удар | 1 фазовый рывок + гарантированное `CORE_STORM` |

Скорости, контактные анимации и HP — конфиги; баланс на тесте в 3 вариантах оружия. Для P1 допускается один переиспользуемый скелет анимации/система без дорогих Humanoid.

## 2. Навигация

Упрощённое групповое steering для обычных врагов, spatial grid, упрощённое обхождение статических препятствий; обновление движения по distance/LOD-бюджету. Враги не должны толкать друг друга физикой, достаточно мягкого separation на логическом уровне. При stuck >2с — обход/мягкое перепозиционирование вне видимости и без урона, метрика `enemy_stuck`. Не телепортировать в упор к игроку.

Структура поведения: `SPAWNING → APPROACH → TELEGRAPH → ATTACK → RECOVER → APPROACH`, и `STAGGER`, `DYING`, `DESPAWN`. У босса свой state graph. Сервер владеет боевым состоянием/HP и решает попадания.

## 3. Приоритет на видимость угроз

- Runner — простой силуэт, эффектная смерть, самая слабая цветовая сигнализация.
- Stalker — заметная подготовка к прыжку и след направления.
- Spitter — кислотный круг на полу **до** урона; без него запрещено запускать атаку.
- Bulwark — большой силуэт, медленное начало атаки, уязвимая область читается сбоку.

В опасный момент не должно одновременно оказаться 8 одинаковых предупреждающих кругов, перекрывающих путь игроку без безопасной зоны. Director регулирует доли и частоту.

## 4. Босс `BOSS_BROODMOTHER` — «Матка разлома»

Силуэт: массивный четырёхлапый инопланетный организм с яркими уязвимыми узлами и двумя центральными отростками. Появляется 7:00 из северных ворот с ~3-секундным аудио/визуальным телеграфом. Первичный HP **4200** для solo P1 (конфиг, под баланс со сформированным билдом); урон по боссу status effect ослаблен по конкретным правилам, не полностью иммунен.

**Фазы:**

- **100–65% HP:** размашистый удар конусом (красный сектор 1.1с до урона); призыв 6–10 бегунов каждые ~14с (ограничен global active cap).
- **65–30%:** удар + «кислотная дорожка» (полосы 2с предупреждения); уязвимые узлы на 5с при промахе тяжелой атаки.
- **30–0%:** рывок на выбранный сектор с 1.4с предупреждения, менее частый призыв. Если время ≥8:00 — усиление давления, но без непрерывных one-shot атак.

Тайм-аут 9:00 → поражение. Все атаки можно избежать базовым движением (рывок облегчает, не является обязательным). Игрок получает окно минимум 3с для DPS после каждого большого приема.

**Победа:** сервер помечает смерть один раз, останавливает спавн, показывает торжество, выдаёт `run_result`. Нельзя получать две награды при одновременных убийствах.

## 5. Режиссёр, health pooling и performance

Пул обычных монстров ограничен конфигом `MaxActiveEnemies` (initial 70). Каждый архетип имеет `spawnCost`: runner=1, stalker=2, spitter=3, bulwark=5, elite=12, boss контролируется отдельно. Общий бюджет — ограничение директора, а не гарантированный каждый кадр зоопарк. Доля особо опасных врагов ≤20% по счётчику. На тестовом телефоне уменьшать cap динамически **между фазами**, если FPS падает; при снижении cap усиливать плотность аудио/FX, но не увеличивать атаки без предупреждения.

## 6. Критерии противников

- 100 последовательных спавнов каждой роли: 0 недоступных/внутристеновых мест.
- Каждая активная атака телеграфируется; нет урона вне её коллайдера.
- После смерти враг никогда не наносит урон и не участвует в поиске цели.
- Статусные эффекты не могут сделать скорость отрицательной, бесконечно заморозить босса или вызвать экспоненциальный proc.
- При KillAll или победе босса освобождаются объекты, коннекты, эффекты, spatial-index записи.

# 06 — PLAYER, CAMERA, HIT FEEL

## 1. Контроллер движения

P1: ходьба speed 16 studs/s, рывок на 16 studs за ~0.25с (CD 5с; не телепортация через геометрию), жизни 100 HP, on-death завершение забега. Базовая игра должна быть проходима без идеальных реакций/доджа и без покупки апгрейдов.

Прыжок в P1 выключен во время боя (арена без платформинга). Случайно включённый Roblox default jump на mobile — UX-дефект. Не перезаписывать постоянные пользовательские глобальные control настройки вне текущего персонажа. Позиция/скорость проверяется на сервере с допусками на лаг и knockback.

## 2. Камера и прицеливание

**Гипотеза управления:** фиксированный elevated third-person, pitch ~50°, camera distance ~55 studs; игрок расположен ~55% высоты экрана. Для ПК WASD + мышь наведение в плоскость XZ, LMB shoot, Space dash, Q Overdrive, Esc menu. Для mobile левый стик движение, правый стик направление стрельбы (shoot-on-aim), Dash и Overdrive две крупные кнопки в правой нижней зоне, без конфликтов с Roblox UI. Альтернативный mobile режим `AUTO_AIM_ASSIST`: ограниченное магнитное притяжение к цели в узком конусе без автоматического убийства. Это нужно сравнить на пользователях, не объявлять выигравшим заранее.

Нельзя стрелять по экранному UI, если там карта/карточки. Server validation не принимает произвольные координаты попадания от клиента.

## 3. Получение урона

- Контактный урон имеет пер-враг cooldown и краткое grace-окно после удара (~0.4с) для читаемости.
- Красный край экрана, короткая отдача камеры, локальный damage marker по направлению. Сильное дрожание камеры по умолчанию выключено или регулируемо.
- HP регенерирует только от разрешённых улучшений/лечения, автоматической регенерации P1 нет.
- При HP<30% звук/визуал предупреждает, но не перекрывает поле боя.

## 4. Overdrive P1

Убийства обычных существ +1 условная единица, элита +10; шкала 0–100, событие убийства зачитывается только сервером. При 100 — доступна активация, длительность **7 секунд** (design target), после чего шкала обнуляется; раннее накопление не переносится. `OD_STANDARD`: +25% rate of fire, +1 пробиваемая цель, усиленная локальная VFX/аудио форма, **без** неуязвимости. Boss kills/ферминг внешними exploit-ремоутами не засчитываются. В P1 нет покупки Overdrive, refill через Robux и pay-to-win.

Overdrive не должен скрывать опасные зоны и анимации атак; низкое качество VFX сохраняет механические преимущества, не картинки. UI шкала заметна, но не занимает центральную область.

## 5. Отклик стрельбы

Первая пуля визуально вылетает сразу на клиенте, server решает реальную цель. Hitmarkers «предсказанное» vs «подтверждённое» не смешивать в статистике, UI корректирует ложные. Стрельба должна быть отзывчивой при обычном ping, без визуальных тонн частиц на каждую пулю. Sound layers: выстрел/пробой/металл/смерть мелкого врага/уникальный crit; лимит одновременно играющих звуков.

## 6. Accessibility

Слайдеры VFX: High/Medium/Low; screen shake off; подсказки направления урона, крупные кнопки, цвет + форма для статуса, не только красный/зелёный; text scale для ключевых экранов. Ретикл обязан оставаться видимым при цепных молниях.

## 7. Обязательные тесты

Рывок не проходит за границы/через толстую стену; мобильный палец не запускает стрельбу при выборе апгрейда; потеря управления на pause и при death невозможна; реальный server health совпадает с UI после сетевой коррекции; нет accidental double fire на touch+mouse.

# 07 — META PROGRESSION & ECONOMY (AFTER P1)

> **Статус:** спецификация следующей фазы. **Не внедрять** сохраняемую экономику до боевого Gate P1 и явного разрешения Gate P2.

## 1. Принцип

Постоянное развитие открывает **выбор** и новые способы игры, а не 100×/1000× усиление урона. Экономика обязана быть объяснима за 10 секунд. Одна мягкая валюта — `SCRAP` («металлолом»), остальные элементы — non-currency трекеры: `BLUEPRINT_PROGRESS`, `WEAPON_MASTERY`, `COSMETIC_COLLECTION`.

## 2. Первые целевые начисления

| Результат | Металлолом (тестовая настройка) |
|---|---:|
| Победа на стандартном уровне | 120 |
| Поражение после 3:00 | 40 |
| Поражение до 3:00 | 15 |
| Бонус за 3 уничтоженных гнезда | +20 |
| Бонус за первый ежедневный **завершённый** забег | +30, один раз в сутки (после P2) |

Начисление серверное, idempotent (`rewardTransactionId`), не покупается прямой боевой урон. Числа — дизайн-гипотезы, по факту будут откорректированы телеметрией времени/скорости открытия.

## 3. Расходы / unlock pacing

- 2-е оружие: **300 SCRAP** (около 3 побед), 3-е: **450 SCRAP** (около 4 побед).
- Новая визуальная ветвь/выбор `mod library`: **200–350 SCRAP** + простой gameplay unlock, но **не** покупка процента урона.
- Мастерство оружия от 1 до 10: опыт за реальные победы/попадания; выдаёт доступ к альтернативным модификациям/косметике и трудным задачам, не бесконечный DPS.
- Постоянный числовой бонус: не больше **+10% суммарного урона и +10% здоровья** ко всем источникам каждого типа даже на максимальном прогрессе, и только после баланс-тестов. Предпочтительнее вообще не добавлять базовые стат-бонусы до проверки потребности.

## 4. Rewards loop без искусственного гринда

Игрок проиграл → получает часть SCRAP, небольшой прогресс mastery, видит конкретную цель следующего забега. Игрок победил → получает ощутимый unlock или прогресс к нему. У новых игроков **не должно быть обязательной 30-минутной стадии слабости**, прежде чем станет весело. Вся базовая петля P1 доступна без любых unlock.

## 5. Persisted profile (предлагаемая схема)

`profileVersion`, `userId`, `scrap`, `unlockedWeapons[]`, `unlockedModules[]`, `masteryByWeapon{}`, `ownedCosmetics[]`, `equippedCosmetics{}`, `firstRunCompleted`, `lifetimeStats{}`, `dailyRewardDate`, `processedRewardIds[]` (bounded FIFO), `updatedAt`. Никаких секретов/платёжных данных в DataStore.

Сохранение/загрузка только server-side через DataStoreService, `UpdateAsync` и `pcall`, bounded retry/backoff и graceful fallback, блокировка дублирующих выдач/покупок. Отдельная миграция версий; если данные не загрузились, **не стирать** профиль новой пустой записью. Ограничить интервал сохранений, учесть API budgets. При `BindToClose` best-effort flush. Dev data в отдельной тестовой среде.

## 6. Контроль exploit

Результат забега и награда вычисляются сервером из подтверждённой state-machine; клиент лишь запрашивает экран. Магазин проверяет достаточность SCRAP на сервере; операции атомарны на уровне профиля; нельзя засчитать один и тот же `runId` дважды.

## 7. Экономические метрики для P2

Среднее SCRAP/30 минут, процент игроков с 2-м оружием после 3–5 побед, доля оставивших игру до первого unlock, среднее число уникальных билдов за 10 забегов, доля пользователей с пустым балансом/застрявшей покупкой. Смена цен требует обновления экономического конфига и журналирования.

# 08 — UI / UX / MOBILE-FIRST

## 1. Информационная архитектура

**P1:** Splash/loading → Start button & gun select → 3-second countdown → Combat HUD → Upgrade choice (3 cards) → Evolution modal → Boss warning & boss HUD → Victory/Defeat results → Replay. Никаких платных окон, push-апсейлов, ежедневных наград до P2/P3.

**Позже:** Hub с оружием, мастерством, миссиями, косметикой, настройками и магазином. Не размещать пять валют на главном экране.

## 2. Боевой HUD (позиции относительные, дизайн-ориентиры)

**Верх-лево:** HP / уровень игрока. **Верх-центр:** фаза, таймер, ограниченный счётчик убийств (не доминирует). **Верх-право:** меню/pause + качество. **Низ-середина:** полоса опыта, Overdrive. **Низ-право:** кнопки Dash и Overdrive с таймером cooldown (на мобильном). **Центр:** прицел/краткие hit markers. Босс — отдельная полоска HP в верхней зоне, не перекрывающая угрозы.

Для landscape телефонов держать центральную игровую область свободной минимум на **55% ширины и 60% высоты** по субъективному зрительному приоритету; это ориентир для макета, проверять на реальных соотношениях сторон. Использовать SafeArea/Gui inset подходящий текущему Roblox API; не делать размеры в фиксированных px без масштабирования. Отступы от системных/Roblox overlays обязательны.

## 3. Мобильный ввод

Левый стик — движение. Правый стик — прицеливание и авто-выстрел при удержании направления. Dash кнопка в зоне правого большого пальца, Overdrive выше; не перекрывать друг друга и край телефона. Важные кнопки: первичный видимый touch-target **не менее ~56×56 условных pixels** на типовой 1080p landscape (проверить через GUI preview и реальные устройства), достаточный зазор. Не «засекречивать» Dash за double tap.

При открытии Upgrade Modal любое удерживаемое touch-aim состояние сбрасывается. По закрытию восстановить только движение/ввод, но не автоматический огонь без нового ввода.

## 4. Выбор улучшения

Три полноширинные/адаптивные карточки: название, иконка, **конкретное изменение** («цепь: 0 → 2 цели»), тип/редкость и сравнение с текущим билдом. Подсветить совместимость с возможной эволюцией, но не навязывать один билд. В соло — игровое время и атаки останавливаются, звук приглушается. Доступна клавиатура 1/2/3 и крупные touch cards. Не выбирать upgrade автоматически в момент появления модала.

## 5. Экран эволюции

Показывает текущую пушку → новую форму, рецепт: `W_ARC_RIFLE + UPG_CHAIN + UPG_RICOCHET + CORE_STORM`, и кнопку «Эволюционировать». После выбора короткая анимация, которой нельзя скрыть урон на сервере: безопасная пауза solo. Переподключение/закрытие модала не должно повторять выдачу.

## 6. Onboarding без стены текста

1. Аватар в подсвеченном круге, стрелка движения, «Двигайся».
2. Первый бегун — подсказка направления второго стика/мыши, «Стреляй».
3. Примерно на 45–60-й секунде — upgrade с одной выделенной рекомендуемой карточкой, но игрок волен выбрать другую.
4. После элиты — первая награда с наглядной связью с эволюцией.

Подсказки исчезают после успешного действия и не блокируют ранний бой. Сохранять флаг завершённого обучения только когда появится P2 profile.

## 7. UI QA checklist

- Портретная ориентация: понятная заставка «Поверни устройство» либо адаптивный режим после отдельного решения; ничего не обрезается молча.
- Тесты минимум 16:9, ~19.5:9, планшетный 4:3, ПК 1080p; реальный touch-тест.
- 3 карточки целиком читаемы; локализация RU/EN; длинные строки не налезают.
- Цветовые состояния обозначены не только цветом (иконки, формы, текст).
- Победа, поражение, ошибка сети и закрытие окна безопасны для повторного нажатия.

# 09 — ROBLOX / LUAU TECH ARCHITECTURE

## 1. Обязательные инженерные принципы

- Roblox server authoritative для HP, damage, спавна, RNG результатов, rewards, cooldowns, доступности эволюций. Клиент: input, камера, UI, VFX/SFX, предикция выстрела.
- Простая дата-ориентированная лёгкая симуляция обычных врагов; не заводить 70 полноценных дорогих Humanoid + pathfinding на каждый tick.
- Все модули конфигурируются через shared read-only definitions, сервер **не** доверяет клиентским копиям и повторно валидирует.
- Только стандартные Roblox/Luau и репозиторные зависимости после аудита. Rojo, Wally, TestEZ — **опциональные**, если уже приняты в проекте; не требовать стороннего платного стека для запуска.
- Поддержать Roblox Studio Play Solo и 2-client Studio test (даже если full-coop отложен), без сетевых exploit дыр.

## 2. Предлагаемая структура (адаптировать существующую, не создавать дубль)

```text
ReplicatedStorage/
  Shared/Definitions/{Weapons,Upgrades,Enemies,RunPhases}.luau
  Shared/Types.luau
  Remotes/{InputFire,InputDash,InputOverdrive,UpgradeSelect,RunSnapshot,FXBatch,RunResult}
ServerScriptService/
  Bootstrap.server.luau
  Services/{RunService,EnemyService,WeaponService,DamageService,
            UpgradeService,DirectorService,EventService,RewardService,AntiAbuseService}
  Systems/{SpatialGrid,EnemySteering,CollisionQueries,ProcBudget}
StarterPlayer/StarterPlayerScripts/
  Controllers/{InputController,CameraController,CombatVFX,HudController,
               UpgradeUIController,AudioController,QualityController}
Workspace/
  Level01/{Geometry,SpawnMarkers,Objects,NavigationHints}
ServerStorage/
  ServerOnlyTemplates/{Enemies,LevelObjects}
```

Скрипты размещаются согласно реальному структурам `.rbxl`/`.rbxlx`/Rojo после аудита; нельзя просто записать дерево папок и заявить, что Studio готова. При наличии существующей игры сначала план миграции.

## 3. Remote contracts (проверяются по типу, времени и состоянию)

- `InputFire(direction: Vector3, clientSequence: number)` — направление нормализовано, ограничен угол/темп, FireRate и состояние оружия проверены сервером. Клиент **не передаёт enemyId и нанесённый damage** как истину. Сервер raycast/shape query по collision layers, ограничение дистанции.
- `InputDash(direction: Vector3, clientSequence: number)` — проверить состояние/кулдаун/дистанцию, защититься от рывка за стену.
- `InputOverdrive(requestSequence: number)` — проверить charge=100 и `ACTIVE`.
- `UpgradeSelect(runId: string, offerId: string, upgradeId: string)` — upgradeId должен быть в текущих 3 предложениях и ещё не выбран; временный `offerId`, consume-once.
- `RunSnapshot` S→C — разреженные authoritative stats, фаза, события, прогресс; `FXBatch` S→C — события для клиентского рендера в бюджете.
- `RunResult` S→C — финальный `runId`, победа/поражение, duration, damage, rewards (P2), без повторных бонусов.

Клиентские RemoteEvents rate-limit per player and command; validate arguments and state; отказ без краша. Не отправлять по сети десятки hit-событий в секунду на каждой цели, если можно агрегировать. Стремиться к прогнозированию локальной картинки при авторитетном серверном damage.

## 4. Enemy simulation и пространственные запросы

- `SpatialGrid`: например cellSize 20 studs, update moving enemy coordinates батчами; seek/radius query O(neighbors) вместо полного поиска на каждом попадании.
- Серверный AI step initial 10Hz для простых преследователей, атаки/состояния по необходимым тикам; визуальная клиентская интерполяция между позициями. Частота — target, не догма.
- У врагов лёгкие модели/скелеты, упрощённые коллизии; навигационные hint-поля и steering вокруг уровня; pathfinding только для редких сложных случаев/босса при необходимости.
- Вражеские смерти и визуальная толпа — клиентские короткие эффекты, контролируемые LOD/cull; server-сущность вовремя удаляется и возвращается в пул.
- Для честности не превращать несуществующую декоративную толпу в дамажащих врагов. Декоративные объекты явно не интерактивны.

## 5. Damage pipeline

`RequestFire → ValidateShot → WorldQuery → DamageResolver → Armor/Status → ProcBudget → Kill/XP/Overdrive → FXBatch`. `damageEvent` содержит `sourceId, runId, targetId, baseDamage, damageType, procDepth, procTags`; `procDepth = 0` первичный, `1` вторичный, `>1` по умолчанию запрещён. Дедупликация по `eventId`/server tick, `maxTargets`, global/per-player proc budget.

**Важное исключение:** описанная в doc.04 синергия «поджог + детонация» — ровно одно допустимое вторичное событие; DOT сам не запускает новую детонацию. Все цепи конечны.

## 6. FPS/Memory/network budgets — предварительные цели, измерить

| Метрика | P1 цель |
|---|---|
| Midrange Android при плотной волне | p95 frame time ≤33.3 мс в 5-мин. тесте (эквивалент целевым ≥30 FPS по 95-му перцентилю), без длительных провалов <25 FPS; измерять реальные frametimes |
| ПК среднего класса | цель 60 FPS; не заявлять как гарантированный результат |
| Одновременные активные враги | начальная гипотеза 70 в solo, cap меняется по профилю |
| Скрипты/физика/рендер | не придумывать жёсткий миллисекундный расклад без MicroProfiler; прикладывать capture и выводы |
| Сеть | не рассылаем покадровые события каждого снаряда каждому клиенту; измерить receive/send KB/s и rate-limit |
| Стабильность | ни одной накопительной утечки по 10 перезапускам забега |

`Workspace.StreamingEnabled` стоит **оценить**, если сцена разрастётся; для компактной арены не включать вслепую и не ломать доступ к критичным моделям. Профилировать MicroProfiler на клиентах и сервере, включая mobile. У LOD есть ступени низких VFX/следов/коротких corpse decals.

## 7. DataStore/Purchases (только P2/P3)

DataStoreService `UpdateAsync`, профиль с `profileVersion`, повторная загрузка без перезаписи при ошибке, idempotent rewards; `ProcessReceipt` обработчик developer products с защитой от повторной выдачи. Не записывать клиентские результаты. После P1 разрешено только записать абстракции, но не запускать магазин.

## 8. Минимальные automated smoke tests

- Нет double-upgrade на повторный `UpgradeSelect`.
- Fire с нелегальным rate/direction не наносит урон.
- `procDepth >1` прекращается, цикл chain bounded.
- У boss reward idempotent.
- Fixed seed даёт ожидаемый offer и spawn-sequence в симулируемом тесте.
- Shutdown/abort освобождает активные враги, UI не зависает.

## 9. Delivery требования

Любое изменение оформляется списком файлов, воспроизводимой командой запуска/сборки, результатами автоматических тестов и manual Studio verification. **Если Studio реально не запускалась, написать «НЕ ПРОВЕРЕНО В STUDIO»**; не подменять проверку статическим обзором Luau. Никакой публикации Production, пользовательских транзакций или перезаписи чужих проектов без отдельного разрешения.

- **Gun evolution:** не только изменение цвета; две геометрические катушки, другая дульная вспышка, изменённый burst pattern.
- **Horde kill:** краткий recoil врага, death animation/collapse до 0.3–0.5с, затем исчезновение/particle дешёвый; минимальные длительные трупы.

## 4. FX LOD

High: полноценные линии цепей + массовые hit particles; Medium: вдвое меньше вторичных частиц/короче трейлы; Low: только первичные попадания, важные сигналы опасности, краткие chain arcs. **Серверный урон одинаков во всех режимах.** Ограничить одновременные звуковые голоса и эмиттеры; secondary VFX можно cull за пределами камеры.

- Начальная стрельба не звучит как пластиковые щелчки; разные типы оружия легко различимы вслепую.
- Игрок видит boss telegraph на максимальной плотности FX.
- Арт-дирекшн утверждается на реальном gameplay кадре со смартфона, не по красивому концепту.
- На P1 нельзя тратить весь срок на детализированные модели, когда стрельба и анимации смерти ещё плохи.
- Не подменять полноценный импорт mesh обещанием `EditableMesh`-генерации: проверить поддержку API и pipeline, для прототипа допустимы локальные Roblox Parts/primitive meshes, но качество оценивается отдельно.

# 11 — MONETIZATION (POST VALIDATION ONLY)

> **Не реализовывать в P0/P1.** Это дорожная карта коммерческой версии после проверки фактического интереса, производительности и правил платформы.

## 3. Запреты

- Нет платных рандомных сундуков или возможности купить увеличение шанса выпадения случайного оружия на старте.
- Нет магазина на первом экране до первого боя/нормального знакомства с игрой.
- Нет ложного таймера, искусственного дефицита, «скоро исчезнет», если это неправда.
- Нет UI, который путает игровую валюту и Robux, и нет deceptive button placement.
- Нет рекламы/монетизации, мешающей прохождению; детей не подталкивать к импульсивным покупкам.

## 4. Проверка коммерческой состоятельности

До решений о сезонном контенте: измерить D1/D7, среднюю длительность сессии, частоту повтора забегов, воронку «начал → завершил → нажал replay», жалобы на фриз/управление. После внедрения магазина: уникальные покупатели, конверсия в покупателя, выручка на пользователя, возвраты/сбои выдачи. Малые выборки/короткие периоды не являются доказательством успеха.

## 5. Архитектура покупки

Не выдавать cosmetic entitlement из клиентского RemoteEvent. Для разовых повторных продуктов — проверенный серверный purchase receipt + идемпотентность и audit; для pass — серверная проверка владения и временный cache. Покупка не должна зависеть от успешности текущего забега; косметика сохраняется и корректно восстанавливается. При ошибке сохранения нельзя делать ложное подтверждение выдачи.

## 6. Marketplace/Compliance checklist

Проверить свежие Roblox правила торговли, подписок, возрастного таргетинга, платного рандома, пользовательских данных, региональной доступности и формата контента. # 12 — BUILD ROADMAP / GATES / DEFINITION OF DONE

## 1. Основное правило

**Astra выполняет только текущий разрешённый Gate**. Не делать лишние системы «впрок». Исключение для стартового задания: P0 и P1A разрешены одним work package, если P0 не выявил блокер. Любой дальнейший переход возможен после отчёта по `agent/DELIVERY_REPORT_TEMPLATE.md` и подтверждения владельца. Непроверенные требования записывать как BLOCKED, не выдавать за DONE.

## P0 — AUDIT / TECH DESIGN / RISK PROBE

**Цель:** понять фактические входные данные и создать исполнимый план. В существующем репо: инвентаризация `.rbxl`/`.rbxlx`, Rojo, зависимостей, assets, namespaces, экрана/контроллера, ошибок и текущей ветки. В пустом репо: предложить минимальный, воспроизводимый pipeline. Допустим минимальный throwaway техэксперимент проверки camera/control или 70 лёгких врагов, но **не** строить всю игру.

**Deliverables:** `docs/IMPLEMENTATION_AUDIT.md`, `docs/TECH_PLAN.md`, issue-list P1, структурный tree, риски, минимальная сборка/Studio инструкции, ADR по несовместимостям. **Gate P0 PASS:** ясно, как открыть проект в Roblox Studio и повторить smoke test, нет несанкционированных публикаций, перечень недостающих входов.

## P1A — MOVEMENT / ARENA / SHOOTING FEEL

**Цель:** 1 арена из doc.02, elevated camera, keyboard/mobile controls, rifle, 2 врага Runner/Stalker, spawn service, hit reaction и death, тест на смартфоне. **Не делать:** мета, сейвы, магазин, босс, 12 upgrades.

**PASS:** первые 15с до первого выстрела, first kill ≤30с у нового тестера, нет дыр в карте/камера не закрывает персонажа, server не принимает fabricated damage, mobile и ПК управляемы, чек-лист звука и попаданий пройден.

## P1B — BUILD SYSTEM / DIRECTOR

**Цель:** 3 базы оружия, 12 улучшений, 2 синергии, одна полная `EV_THUNDERLORD`, элита, Overdrive, устойчивый 8-минутный сценарий. Спавн/kill/proc budget; элементарный upgrade UI.

**PASS:** все 12 определённых модификаторов доступны и работают согласно doc.04; две синергии воспроизводимы deterministic seed; ≥2 различимые сборки; 0 infinite proc; эволюция доступна при выполнении рецепта; 10 автоматизированных/ручных забегов без soft lock.

## P1C — BOSS / UI / VFX / MOBILE PERF

**Цель:** boss, скриптовое событие Hive, финал/результат, полноценный HUD, анимации, SFX, LOD, QA/analytics instrumentation. Mobile quality profiles. Нет постоянной экономики/магазина.

**PASS (закрытый вертикальный срез):**

1. В 10 последовательных соло-забегах не происходят hard-lock / бесконечные RunState / потерянные профили (профилей ещё нет).
2. Все 4 archetype, elite, boss и событие корректно работают; игрок в конце либо победил, либо понятно проиграл, ≤9:00.
3. Реальный **midrange Android** (конкретная модель/OS указывается в отчёте) — p95 frame time ≤33.3 мс в пике (целевой уровень ≥30 FPS), без регулярных затяжных провалов <25 FPS; если теста нет → BLOCKED, а не PASS.
4. На mobile и ПК игрок при выборе upgrade не получает damage (solo pause) и сохраняет ввод после.
5. При снижении качества до Low каждая атака босса остаётся читаемой, damage mechanics неизменны.
6. Базовый exploit-check: поддельные fire/upgrade/overdrive запросы не дают преимуществ.
7. Слепой тест минимум 10–15 людей не из команды; ориентир ≥60% добровольно хотят повторить забег. Малую выборку явно отмечать как ориентир, не доказательство PMF.

После PASS — **STOP + REVIEW:** честный отчёт о понравившемся/скучном, главной причине смерти/выхода, корректировки GDD. Никакой автогенерации новых миров без продуктового решения.

## P2 — PERSISTENCE / META / COOP PROTOTYPE

**Только после P1 и одобрения.** Одно из двух направлений в первую очередь: A) постоянные профили/мастерство и economy из doc.07; B) 2-player coop prototype. Не брать оба в параллель без нового плана и рисков. После них можно расширить кооп до 4 игроков, прогнать сетевые тесты и пере-балансировать director per party.

**PASS:** migration-safe saves, нет double rewards и lost purchases, кооп (если включен) корректно делит HP/агро и не ломает pause logic, telemetry.

## P3 — PRODUCT LAUNCH PREP

Только после измерений P2: дополнительные формы/биом, подготовка коммерческого SDK, RU/EN локализация, privacy/content compliance, продуктовая аналитика, косметический магазин, soft launch и iterative balancing. Конкретные SKU/цены утверждает владелец и публикует в Creator Dashboard только после отдельного разрешения.

## 2. Definition of Done для **каждого** Gate

- Diff ограничен scope; изменённые файлы перечислены.
- Архитектура/контракты и конфиги синхронизированы с документацией.
- Code smoke tests + Studio manual проверка **фактически** выполнены или отмечены как NOT TESTED.
- Тестовая платформа, устройство, FPS/duration указаны при performance claims.
- Нет блокирующих performance, gameplay, anti-exploit проблем по критериям Gate.
- Есть скриншоты/короткая запись реального gameplay, если визуальный Gate.
- `DEVIATIONS.md` фиксирует все расхождения, включая несогласованные идеи агента.
- Есть следующая рекомендуемая команда и STOP; запуск следующего Gate — только после разрешения.

# 13 — QA, PLAYTEST & ANALYTICS

## 1. Главный исследовательский вопрос

**«Хочется ли сделать второй забег?»** Внутриигровые FPS и pass tests нужны, но не равны увлекательности. Независимые 10–15 участников — начальный сигнал, а не статистическая валидация D1/D7.

## 2. Playtest формат

Участник без контекста и разработческих подсказок играет два сценария: 1) первый заход до завершения; 2) при желании запускает второй. Интервью после: «когда стало интересно/скучно?», «какое улучшение действительно изменило бой?», «что убило?», «хочешь ещё раз и почему?». Фиксировать наблюдения, а не внушённые ответы.

## 3. Instrumentation P1 (в dev/telemetry без личных данных)

| Event | Поля | Применение |
|---|---|---|
| `run_start` | sessionId, runId, deviceClass, buildVersion, seed | воронка |
| `first_shot` | elapsed, weaponId | time-to-action |
| `first_kill` | elapsed | first fun |
| `upgrade_offer` | elapsed, offerId, 3 upgrade IDs | качество RNG |
| `upgrade_choice` | elapsed, upgradeId, offeredIds | предпочтения |
| `elite_kill` | elapsed, eliteId | pacing |
| `weapon_evolved` | elapsed, evolutionId | достижение power spike |
| `hive_event_result` | completedNests, elapsed | цель внутри рана |
| `boss_start/boss_end` | elapsed, bossHp/killCause | сложность |
| `run_end` | result, elapsed, lastHp, deathCause, kills, damage, build | исход |
| `replay_clicked` | elapsedSinceEnd | непосредственная заинтересованность |
| `perf_sample` | platform, elapsed, avgFps/p95FrameMs, enemyCount, vfxLevel | оптимизация |

Точные telemetry API/хранилище Astra выбирает после аудита без внешних аналитических платных сервисов по умолчанию. Не сохранять IP, device identifiers или другие ненужные персональные данные.

## 4. Основные гипотезы и targets

| Метрика | Первичный критерий |
|---|---|
| Время до первого выстрела | ≤15с для большинства новых пользователей |
| Время до первого убийства | ≤30с |
| Время до первого meaningful upgrade | ≤60с |
| Попытка добровольного replay после первого завершения | ≥60% в закрытом слепом тесте, порог гипотеза |
| Длина победного прохождения | 7:30–8:30 типично; hard cap 9:00 |
| Процент проигрышей на boss | измерить, скорректировать по feedback, не фиксировать искусственную целевую долю |
| D1/D7 retention, DAU, ARPDAU | **только после публичных данных**, не выдумывать |

## 5. Функциональная матрица

- **Game flow:** escape/pause, повторная смерть, disconnect/reconnect, death during modal, replay, boss death в один кадр с player death (серверная детерминированная precedence rule: boss death → victory, если сервер обработал смерть босса прежде player-death; зафиксировать event order).
- **Combat:** hit through wall, burst from client, cooldown hacks, attack outside map, multihit collision, negative health, damage after death, chain cycles.
- **Upgrades:** menu opened twice, selection stale offer, 2 simultaneous selection events, missing recipe key, inactive menu, RF spam.
- **Enemies:** 100 spawn points, path blockage after gate, `NoTarget` under interruption, 10 sequential runs no instance leaks.
- **Visual/mobile:** bad aspect, obstruction, frame drops, screen shake, dash at edge, boss telegraph under low graphics, UI close during shooting.
- **Network:** packet jitter/lag test with simulated latency if feasible, untrusted client, server overload, listener cleanup.

## 6. Repro steps / bug report

Каждая ошибка: build hash, actual platform, screenshot/video, runSeed, time into run, expected, actual, severity, repro, root-cause hypothesis and verified fix. Не объявлять perf improvements без identical-device before/after measurement.

## 7. Visual acceptance

Видеозапись с **реального телефона**, 60–90с: старт, стрельба, гибель толпы, upgrade, эволюция, босс, HUD. Скриншоты игровой камеры, а не только Studio Scene View. Отдельно low VFX доказательство читаемости.

# 14 — DECISIONS, OPEN QUESTIONS & RISKS

## 1. Зафиксированные проектные ограничения (baseline для агентской работы)

- Genre: Roblox PvE horde-shooter, акцент на ручной стрельбе и ощущении силы; не Vampire Survivors-клон с полным авто-боем.
- Геймплейная новизна: эволюция оружия из свойств монстров + ограниченные цепные реакции.
- P1: только solo, 1 арена, 8-минутный забег, 3 оружия, 12 модификаторов, 4 архетипа, элита, босс, 2 синергии, 1 доведённая эволюция.
- Камера: elevated third-person как основная гипотеза. Разработка должна позволять менять дистанцию/питч без переписывания стрельбы.
- Первая арена: Reactor Yard ~360×320 studs; события в doc.02; изменения геометрии скриптовые и детерминированные.
- Mobile-first с поддержкой ПК; quality scaling; серверная авторитетность.
- Монетизация и постоянная экономика запрещены до следующего явно открытого Gate.

**Примечание:** это зафиксированная **рабочая спецификация по переписке**, а не доказательство того, что пользователь утвердил каждый числовой параметр. Числа остаются гипотезами до playtest.

## 2. Открытые продуктовые решения, где нужно мнение владельца позднее

| ID | Решение | Рабочая гипотеза | Когда решить |
|---|---|---|---|
| O-01 | Финальное название и права | SWARMFALL — временное | перед публикацией |
| O-02 | Камера | fixed elevated 50°, ~55 studs | после P1A mobile tests |
| O-03 | Mobile combat | right stick shoots + aim assist | после первых 5 игроков |
| O-04 | Реальное количество live врагов | cap 70 solo | по profiling P1B/C |
| O-05 | Кооперативный pause/upgrade | карты между микроволнами | P2 |
| O-06 | Варианты постоянной силы | max +10% или вообще без бонуса | P2 economy |
| O-07 | Монетизация SKU и цена | cosmetic-only | после реальных данных P2 |
| O-08 | Контентный рейтинг и возрастные ограничения | по фактически реализованному содержимому | перед публикацией |

## 3. Архитектурные риски

| Риск | Вероятность/влияние | Действие |
|---|---|---|
| Слабая стрельба / безвкусные hit effects | высокая / критическое | закрыть P1A до усложнений |
| Сложный AI на сотнях существ ломает mobile | высокая / критическое | data-oriented steering, enemy cap, реальный профиль |
| Урон на сервере ощущается с лагом | средняя / высокая | client prediction + server authority, rate limiting |
| Мульти-цепи вызывают exp growth | высокая / высокая | procDepth и budget, QA |
| RNG блокирует первую эволюцию | высокая / высокая | гарантированный core/pity через элиту |
| Арена превращается в пустую коробку | средняя / высокая | секторность/события/обходы/визуальные ориентиры |
| Отдельная монетизация уничтожает баланс | средняя / высокая | косметика only, gate |
| Агент «сделал все» без запуска Studio | высокая / критическое | строгая честная отчётность и Gate, видеоприёмка |
| ТЗ и текущий repo конфликтуют | неизвестно / высокое | audit first, ADR, запрет молчаливой перезаписи |

## 4. Что Астра может предложить, но НЕ внедрять без согласования

Смена управления на авто-атаку, переработка жанра в extraction/tycoon, новые питомцы, торговля, бесконечные большие уровни, сезонный пропуск до геймплейного теста, расширение команды до кооп, замена модели врагов на дорогих Humanoid. Предложения оформлять как ADR: цель, аргументы, риск, цена, альтернативы, критерии проверки.

## 5. Ключевой стоп-сигнал

Если P1A «стрелять не приятно» — приостановить P1B. Если P1C mobile FPS ниже целевого/читабельность низкая — не строить P2. Если добровольный replay ниже ожидаемого — анализировать босса, pacing, weapon feel, а не добавлять валюты и магазин.

# 15 — DATA CONTRACTS & CONFIGURATION

> Псевдоструктуры иллюстрируют контракты. Это **не готовый Luau код** и не повод Astra пропускать типизацию, реальные тесты и аудит существующего проекта.

## 1. Идентификаторы, которые должны оставаться стабильными

```text
MAP_REACTOR_YARD
RUN_STANDARD_SOLO
W_ARC_RIFLE, W_SCATTERGUN, W_PLASMA_BEAM
EV_THUNDERLORD, EV_INFERNO_GRINDER, EV_VOID_LANCE
CORE_STORM, CORE_EMBER, CORE_VOID
EN_RUNNER, EN_STALKER, EN_SPITTER, EN_BULWARK
ELITE_BULWARK, BOSS_BROODMOTHER
OBJECT_COIL, OBJECT_GATE, OBJECT_HIVE
EVENT_HIVE_BREACH
SYN_CHAIN_RICOCHET, SYN_IGNITE_DETONATE
```

Модули upgrade: `UPG_CHAIN`, `UPG_RICOCHET`, `UPG_PIERCE`, `UPG_IGNITE`, `UPG_DETONATE`, `UPG_CORRODE`, `UPG_FREEZE`, `UPG_MULTISHOT`, `UPG_FIRERATE`, `UPG_CRIT`, `UPG_DASH_SHOCK`, `UPG_SHIELD`.

## 2. Примеры typed config (псевдо-Luau)

```lua
RunConfig = {
  id = "RUN_STANDARD_SOLO",
  levelId = "MAP_REACTOR_YARD",
  targetSeconds = 480, hardLimitSeconds = 540,
  bossStartSeconds = 420,
  starterWeaponId = "W_ARC_RIFLE",
  spawnActiveCap = 70, -- placeholder, real-device profile mandatory
  runSeed = nil, -- assigned on server
}

WeaponDefinition = {
  id = "W_ARC_RIFLE",
  shotDamage = 12, roundsPerSecond = 6, rangeStuds = 85,
  magazine = 36, reloadSeconds = 1.5,
  allowedUpgrades = {"UPG_CHAIN", "UPG_RICOCHET", "UPG_PIERCE"},
}

EvolutionRecipe = {
  id = "EV_THUNDERLORD", baseWeapon = "W_ARC_RIFLE",
  requiredUpgrades = {"UPG_CHAIN", "UPG_RICOCHET"},
  requiredCore = "CORE_STORM",
  requiresExplicitPlayerConfirmation = true,
}
```

## 3. Authoritative run state (пример интерфейса)

```text
RunState {
  runId: string, ownerUserId: number, seed: number,
  phase: "PREPARE"|"ACTIVE"|"UPGRADE"|"EVENT"|"BOSS"|"FINISHED",
  elapsedSeconds: number, playerHealth: number,
  weaponId: WeaponId, activeUpgrades: set<UpgradeId>,
  availableCores: set<CoreId>, evolutionId?: EvolutionId,
  overdriveCharge: number, aliveEnemiesById: map<EnemyId, EnemyState>,
  selectedOfferId?: string, selectedChoices?: UpgradeId[3],
  accumulatedXP: number, eventFlags: map<string,bool>,
  result?: {outcome: "VICTORY"|"DEFEAT"|"ABORT", reason:string}
}
```

При соло-паузе используйте отдельный `effectiveSimulationElapsed`: фаза не движется, враги не наносят урон, дот не тикает. Серверный wall-clock нужен отдельно для диагностики и ограничений, не должен перескакивать gameplay время.

## 4. Registry & validation

Все IDs проверять при startup: отсутствующие референсы модификаторов/ядра/модели должны логировать явную ошибку/не запускать повреждённый run. Нельзя выдавать `nil` weapon. Схемы конфигов — централизованные shared enums; сервер по ID находит собственный authoritative data. Клиент не управляет произвольными JSON/Instances от собственного имени.

## 5. Debug seeds и тестовые конфигурации

`SEED_FEEL_01`: starter, runner, первый upgrade chain. `SEED_EVOLUTION_01`: chain→ricochet→elite core→Thunderlord. `SEED_FIRE_01`: ignite + detonate и 20 целей. `SEED_BOSS_01`: полный билд, старт босса. Реальные числовые seed значения разработчик назначает в фикстурах и записывает, не притворяться, что фиксированные имена гарантируют одни и те же RNG результаты до реализации.

## 6. Version compatibility

Config registry version и save profile version не путать. При удалении upgrade из контента иметь fallback mapping/reconcile для старых профилей после P2. Все сериализуемые поля явно ограничены типами, списки capped. `RunResult` отправляется ровно один раз клиенту логически; повтор транспорта не порождает повторную выдачу.
